# PRD — O.S.A. (Операционная Система Агента)

> Product Requirements Document. Скоуп MVP (слоя 1). На основе `VISION.md` и `BRIEF.md`.

---

## 1. Резюме

**O.S.A. v0.1** — goal-driven эволюционирующий агент, который работает на одной машине 24/7. Принимает глобальную цель, сам декомпозирует её в подзадачи, решает всеми доступными инструментами, накапливает опыт и меняет своё поведение со временем.

**Главное отличие от готовых фреймворков**: агент не ждёт пошаговых инструкций. Получил цель — и работает до результата, сам принимая решения о следующих шагах.

**Целевой юзер**: один разработчик (Михаил). На MVP других пользователей не предполагается.

---

## 2. Цели (Goals)

| # | Цель | Измеримость |
|---|------|-------------|
| G1 | Агент запускается как процесс, не падает 24 часа | uptime 99% на dev-машине |
| G2 | Принимает цель на естественном языке и решает её автономно | 5 эталонных целей, решает ≥3 без вмешательства |
| G3 | Сам ставит себе подзадачи и перепланирует при сбоях | лог показывает дерево подзадач |
| G4 | Накапливает опыт (skills) и переиспользует при следующих целях | библиотека skills растёт, hit rate растёт |
| G5 | Сам меняет поведение (промпты, стратегии) на основе опыта | версия системного промпта версионируется, diff виден |
| G6 | Маленькая модель + scaffolding > голая маленькая модель на тех же задачах | бенчмарк: ≥30% прирост успешности на эталонных целях |

---

## 3. Не в скоупе (Non-Goals) для MVP

- ❌ UI в браузере, Telegram-бот, мобильное приложение — только CLI
- ❌ Мультиагент (несколько ролей) — один агент с богатым инструментарием
- ❌ Bare-metal install — это слой 2, отдельный трек
- ❌ Mesh из нескольких устройств — слой 3, отдельный трек
- ❌ Веб-дашборд — CLI + структурные логи достаточно
- ❌ GUI для конфигурации — только TOML-файл
- ❌ Поддержка нескольких LLM-провайдеров одновременно — один основной + заглушка
- ❌ Распределённые вычисления на старте
- ❌ RAG над большой базой знаний — knowledge base ограничен локальными файлами + skills

## 4. Юзер-сценарии (User Stories)

### US1. Постановка глобальной цели
**Как** пользователь, **я хочу** сказать агенту одну большую цель и забыть.
```
$ osa goal "настрой мне VPN-сервер на этом компе, чтобы я мог ходить в интернет через него с телефона"
[OSA] Принял цель. Декомпозирую...
[OSA] План:
  1. Проверить установленные пакеты (openvpn, wireguard, ...)
  2. Выбрать протокол на основе доступности
  3. Сгенерировать конфиги
  4. Запустить сервис
  5. Проверить, что порт слушается
  6. Создать конфиг для клиента
[OSA] Начинаю выполнение. Лог: osa logs --follow
```
Пользователь уходит. Агент работает. Возвращается — готово или список вопросов.

### US2. Прерывание и продолжение
**Как** пользователь, **я хочу** остановить агента (Ctrl-C или `osa stop`) и потом продолжить с того же места.
```
$ osa stop
[OSA] Состояние сохранено. Подзадача 3 из 6 в процессе.
$ osa start
[OSA] Возобновляю с подзадачи 3.
```

### US3. Вмешательство (human-in-the-loop)
**Как** пользователь, **я хочу** получать подтверждение перед опасными действиями (rm, внешние HTTP-запросы с побочками, изменение системных файлов).
```
[OSA] Хочу выполнить: sudo apt install wireguard
[OSA] Это безопасное действие, но требует sudo.
[OSA] Разрешить? [y/N/dry-run/details]: y
```

### US4. Инспекция состояния
**Как** пользователь, **я хочу** видеть, что агент делает прямо сейчас и что делал раньше.
```
$ osa status
Цель: настрой VPN-сервер
Текущая подзадача: 3/6 — сгенерировать конфиги
Итерация: 4, токенов потрачено: 12 341
Аптайм: 2ч 14м

$ osa logs --follow
2026-09-23 14:22:11 [think] Нужно проверить, установлен ли wireguard...
2026-09-23 14:22:13 [act]   shell: which wireguard
2026-09-23 14:22:14 [obs]   путь не найден
...
```

### US5. Skill reuse
**Как** пользователь, **я хочу** чтобы при следующей похожей цели агент использовал накопленный опыт.
```
$ osa skills list
- install-package: установка пакета через apt/pip/npm (использовался 7 раз)
- write-config: запись TOML-конфига с шаблоном (4 раза)
- check-port-open: проверка, слушается ли порт (3 раза)
- ...
```

### US6. Эволюция поведения
**Как** пользователь, **я хочу** видеть, как агент меняет свои промпты и стратегии на основе опыта.
```
$ osa evolution show
Версия системного промпта: v7
Изменения v6 → v7:
  + Добавлен раздел «Когда использовать готовый skill vs импровизировать»
  - Удалён устаревший совет «всегда спрашивай пользователя перед shell»
Метрика успешности за последние 10 целей:
  v5: 6/10 успешно
  v6: 7/10 успешно
  v7: 8/10 успешно (предварительно, n=3)
```

## 5. Функциональные требования

### 5.1. Runtime
- F1.1. Процесс-демон, запускается через `osa start`, останавливается через `osa stop` или Ctrl-C.
- F1.2. Graceful shutdown: при SIGTERM сохраняет состояние в БД за ≤2 секунды.
- F1.3. Автоперезапуск при крэшах (опционально через systemd / NSSM / launchd — out of MVP, делаем вручную).
- F1.4. Watchdog: если LLM не отвечает N секунд, отменяет шаг и пробует другую стратегию.
- F1.5. Лимит итераций на одну цель (по умолчанию 100), лимит токенов (по умолчанию 1M), лимит времени (24ч по умолчанию).

### 5.2. Goal Engine
- F2.1. Принимает цель в свободной форме (`osa goal "..."`).
- F2.2. Декомпозирует цель в дерево подзадач (Plan-and-Execute).
- F2.3. Выполняет подзадачи последовательно или параллельно (если независимы).
- F2.4. Перепланирует при сбое шага (не 3 раза подряд одно и то же).
- F2.5. Возобновляется после рестарта с места остановки.

### 5.3. Memory
- F3.1. Краткосрочная: контекст текущей сессии в памяти процесса + в SQLite.
- F3.2. Долгосрочная: факты, события, заметки в SQLite (`memory_facts` table).
- F3.3. Эпизодическая: лог всех действий с временными метками (`episodes` table).
- F3.4. Семантический поиск: факты ищутся по embedding similarity (опционально для MVP, но архитектура готова).

### 5.4. Skills (опыт)
- F4.1. Skill = reusable процедура, привязанная к типу задачи. Структура: `name`, `description`, `params`, `code_or_steps`, `success_count`, `fail_count`.
- F4.2. Агент создаёт skill автоматически, когда успешно решает повторяющийся паттерн.
- F4.3. Агент использует существующий skill, если семантически подходит.
- F4.4. Skill может быть «promoted» (проверен и стабилен) или «experimental» (новый, требует подтверждения).
- F4.5. Skills версионируются.

### 5.5. Evolution (самоизменение)
- F5.1. Системный промпт хранится в БД, не в коде. Версионируется.
- F5.2. После каждой цели агент делает рефлексию: что сработало, что нет, что улучшить.
- F5.3. На основе рефлексии агент предлагает изменения промпта/стратегии.
- F5.4. Изменения промпта применяются автоматически только если метрика успешности падала. Иначе — в очередь на review пользователя.
- F5.5. Все изменения логируются с возможностью отката.

### 5.6. Tool Sandbox
- F6.1. Все инструменты работают в `$OSA_HOME/sandbox/`. Никакого доступа к пользовательским файлам.
- F6.2. Базовые инструменты MVP:
  - `file_read(path)`, `file_write(path, content)`, `file_list(dir)`
  - `shell(cmd, timeout, cwd=sandbox)` — с human-in-the-loop по умолчанию
  - `http_get(url)`, `http_post(url, data)`
  - `web_search(query)`
  - `time()`, `date()`
  - `goal_status()`, `goal_pause()`, `goal_resume()`
- F6.3. Любой tool может быть dry-run'ом (выполняется, но без побочек, если возможно).
- F6.4. Все вызовы логируются с аргументами и результатом.

### 5.7. LLM-провайдер
- F7.1. Абстрактный интерфейс `LLMProvider`: `complete(messages, tools, **kwargs)`.
- F7.2. Основной бэкенд: Minimax (через OpenAI-совместимый API).
- F7.3. Fallback бэкенд: локальный stub (для тестов без API).
- F7.4. Стратегия ротации: если один упал N раз, переключаемся на другой.
- F7.5. Конфиг: API-ключ в env, остальное в TOML.

### 5.8. CLI
- F8.1. `osa init` — инициализация `$OSA_HOME` (папка + БД + конфиг).
- F8.2. `osa start` — запуск демона.
- F8.3. `osa stop` — graceful остановка.
- F8.4. `osa goal "..."` — постановка новой цели (синхронно: ждёт план или асинхронно: в очередь).
- F8.5. `osa status` — текущее состояние.
- F8.6. `osa logs [--follow] [--level=debug]` — структурные логи.
- F8.7. `osa skills list|show|forget` — управление skills.
- F8.8. `osa evolution show|diff|rollback` — управление эволюцией.
- F8.9. `osa task list|add|cancel` — низкоуровневое управление подзадачами.

## 6. Нефункциональные требования

- N1. **Запуск**: `git clone && uv sync && uv run osa init && uv run osa start`. Без Docker.
- N2. **Хранилище**: `$XDG_DATA_HOME/osa/` (на Windows: `%LOCALAPPDATA%/osa/`). Структура:
  ```
  osa/
  ├── osa.db              # SQLite: goals, tasks, memory, skills, episodes
  ├── sandbox/            # рабочая папка агента
  ├── logs/               # структурные логи (structlog JSON)
  ├── config.toml         # настройки
  └── prompts/            # версионированные системные промпты
  ```
- N3. **Тесты**: pytest, покрытие ядра ≥70%. Минимум: unit-тесты для каждого компонента, 3 интеграционных теста с моком LLM.
- N4. **CI**: GitHub Actions, запуск тестов на каждый push.
- N5. **Производительность**: старт демона ≤3 секунд, отклик CLI-команд ≤500мс.
- N6. **Документация**: README с быстрым стартом, ARCHITECTURE.md с диаграммой компонентов, ADR/ для ключевых решений.

## 7. Архитектура (высокоуровневая)

```
┌─────────────────────────────────────────────────────────────┐
│                         CLI (typer)                         │
│  init | start | stop | goal | status | logs | skills | ...  │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│                    OSA Runtime (демон)                       │
│                                                              │
│  ┌──────────┐    ┌──────────┐    ┌──────────────┐            │
│  │ Goal     │◄──►│ Task     │◄──►│  ReAct Loop  │            │
│  │ Engine   │    │ Planner  │    │ (think-act-  │            │
│  │          │    │          │    │  observe)    │            │
│  └──────────┘    └──────────┘    └──────┬───────┘            │
│                                          │                   │
│  ┌──────────┐    ┌──────────┐    ┌──────▼───────┐            │
│  │ Memory   │    │ Skills   │    │    Tools     │            │
│  │ Store    │    │ Library  │    │   Sandbox    │            │
│  └──────────┘    └──────────┘    └──────┬───────┘            │
│                                          │                   │
│  ┌──────────┐    ┌──────────┐    ┌──────▼───────┐            │
│  │Evolution │    │  LLM     │◄──►│  Toolcalls   │            │
│  │ Manager  │    │ Provider │    │   Logger     │            │
│  └──────────┘    └──────────┘    └──────────────┘            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
                           │
                           ▼
                  ┌──────────────────┐
                  │  SQLite Database │
                  │  (goals, tasks,  │
                  │  memory, skills) │
                  └──────────────────┘
```

Компоненты:
- **Goal Engine** — принимает цель, разбивает на подзадачи, следит за прогрессом
- **Task Planner** — оркестрирует выполнение подзадач, перепланирует при сбоях
- **ReAct Loop** — базовый цикл think-act-observe
- **Memory Store** — краткосрочная (в RAM + SQLite), долгосрочная (SQLite), эпизодическая (лог)
- **Skills Library** — накопленный опыт в виде reusable-процедур
- **Tools Sandbox** — изолированные инструменты, работают только в `$OSA_HOME/sandbox/`
- **Evolution Manager** — рефлексия + версионирование промптов + автоматические улучшения
- **LLM Provider** — абстракция, Minimax сейчас, локальная 1B потом

## 8. Модель данных (БД)

```sql
-- Цели
CREATE TABLE goals (
  id INTEGER PRIMARY KEY,
  description TEXT NOT NULL,
  status TEXT NOT NULL,  -- pending, planning, running, paused, done, failed
  plan_json TEXT,         -- дерево подзадач
  created_at TIMESTAMP,
  updated_at TIMESTAMP,
  finished_at TIMESTAMP
);

-- Подзадачи
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY,
  goal_id INTEGER REFERENCES goals(id),
  parent_id INTEGER REFERENCES tasks(id),  -- NULL = корень
  description TEXT NOT NULL,
  status TEXT NOT NULL,  -- pending, running, done, failed, blocked
  result TEXT,
  attempts INTEGER DEFAULT 0,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

-- Эпизоды (каждое действие)
CREATE TABLE episodes (
  id INTEGER PRIMARY KEY,
  task_id INTEGER REFERENCES tasks(id),
  step_type TEXT,  -- think, act, observe, reflect
  content TEXT,
  tool_name TEXT,
  tool_args TEXT,
  tokens_used INTEGER,
  created_at TIMESTAMP
);

-- Долгосрочная память (факты)
CREATE TABLE memory_facts (
  id INTEGER PRIMARY KEY,
  content TEXT NOT NULL,
  embedding BLOB,  -- опционально, для семантического поиска
  source_task_id INTEGER REFERENCES tasks(id),
  importance REAL,  -- 0..1, для приоритизации при recall
  created_at TIMESTAMP,
  last_used_at TIMESTAMP
);

-- Skills (опыт)
CREATE TABLE skills (
  id INTEGER PRIMARY KEY,
  name TEXT UNIQUE NOT NULL,
  description TEXT NOT NULL,
  params_schema TEXT,    -- JSON Schema
  steps_json TEXT,        -- шаги или код
  status TEXT,            -- experimental, promoted, deprecated
  version INTEGER DEFAULT 1,
  success_count INTEGER DEFAULT 0,
  fail_count INTEGER DEFAULT 0,
  created_at TIMESTAMP,
  last_used_at TIMESTAMP
);

-- Версии системного промпта
CREATE TABLE prompt_versions (
  id INTEGER PRIMARY KEY,
  version INTEGER NOT NULL,
  content TEXT NOT NULL,
  reason TEXT,  -- почему изменили
  metric_before REAL,
  metric_after REAL,
  active BOOLEAN DEFAULT 0,
  created_at TIMESTAMP
);
```

## 9. Критерии приёмки MVP (M1)

**Definition of Done для MVP**:

- [ ] **D1**. Проект инициализирован: `git clone && uv sync && uv run osa init` работает.
- [ ] **D2**. Демон запускается и не падает 24 часа (тест вручную, не в CI).
- [ ] **D3**. CLI-команды `start|stop|status|logs|goal|skills|evolution` работают.
- [ ] **D4**. Goal Engine: принимает цель, декомпозирует в план из 3+ подзадач.
- [ ] **D5**. ReAct Loop: выполняет подзадачу через think-act-observe.
- [ ] **D6**. Все 5 базовых инструментов работают (file, shell, http, web_search, time).
- [ ] **D7**. Human-in-the-loop для shell-команд, требующих sudo или записи вне sandbox.
- [ ] **D8**. Память: факт записывается и достаётся в следующей сессии.
- [ ] **D9**. Skills: агент создал skill после первой успешной задачи и переиспользовал во второй.
- [ ] **D10**. Evolution: системный промпт версионируется, есть механизм рефлексии.
- [ ] **D11**. Graceful shutdown: Ctrl-C сохраняет состояние за ≤2 секунды.
- [ ] **D12**. Возобновление: после рестарта агент продолжает с того же места.
- [ ] **D13**. Лимиты: при превышении итераций/токенов/времени агент останавливается с понятной ошибкой.
- [ ] **D14**. Логи: структурный JSON, можно грепать.
- [ ] **D15**. Тесты: pytest, покрытие ядра ≥70%, 3 интеграционных теста с моком LLM.
- [ ] **D16**. CI: GitHub Actions зелёный.
- [ ] **D17**. README + ARCHITECTURE.md.
- [ ] **D18**. **Бенчмарк**: 3 эталонные цели, агент решает ≥2 из 3 автономно (без подсказок).
- [ ] **D19**. **Сравнение**: те же 3 цели голой Minimax без scaffolding — решает ≤1 из 3.

**Эталонные цели для бенчмарка** (предварительно, уточним в M0):
1. «Создай в sandbox/ проект hello-world на Python, инициализируй git, сделай первый коммит, запусти тесты»
2. «Найди в интернете 5 публичных API погоды, выбери самый простой без ключа, напиши в sandbox/ скрипт который показывает погоду в Москве»
3. «Прочитай README.md из sandbox/, найди в нём все TODO/FIXME, составь таблицу в sandbox/todos.md»

## 10. Открытые вопросы на старте M0

1. Имя модуля Python: `osa` / `osa_runtime` / `osagent`? — выберу `osa`, как самое короткое.
2. Расположение кода: всё в `src/osa/` или плоско в `src/`? — выберу `src/osa/` для тестируемости.
3. Будем ли коммитить `pyproject.toml` с lock-файлом? — да, `uv.lock` в репо.
4. Дефолтный лимит итераций — 100 на цель, или меньше для тестов? — 100 для прод, 20 для тестов.
5. Дефолтный лимит токенов — 1M на цель? — да, настраивается в конфиге.
6. Как называть skills — snake_case или kebab-case? — `kebab-case` (как в npm).
7. Конфиг — TOML или YAML? — TOML (стандарт в Python через `tomllib`).

Эти вопросы решу сам, если не возразишь.
