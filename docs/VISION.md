# Vision проекта O.S.A.

> **O.S.A.** — **О**перационная **С**истема **А**гента.
> Полное имя рабочее, может поменяться. Произносится как «оса».

---

## Большая идея (в одном абзаце)

Мир тонет в e-waste: тонны рабочего железа уходят на свалку, потому что его невыгодно переиспользовать. Параллельно LLM-индустрия тратит миллиарды на гигантские модели, хотя есть исследования, что **маленькая модель с правильным scaffolding-фреймворком решает задачи на уровне большой** (Anthropic, DeepMind, 2024–2025 — agentic scaling vs model scaling).

**O.S.A. соединяет эти две идеи.** Фреймворк, который превращает маленькую локальную LLM в автономного агента, способного решать реальные задачи. Агент ставится на старое железо, берёт его целиком как ресурс, объединяет несколько таких машин в mesh — и получается распределённый мозг из хлама, который не уступает дорогим кластерам по эффективности на конкретных задачах.

**Формула проекта**:
> маленькая LLM (~1B) + мощный scaffolding-фреймворк = агент, решающий задачи, с которыми не справляется сама модель без фреймворка.

---

## Философия (зачем это вообще)

### 1. Маленькая модель — не слабость, а ограничение, которое заставляет делать хороший фреймворк
Большая модель «угадывает» правильный ответ за счёт brute-force знаний. Маленькая модель **вынуждена думать структурно**: декомпозиция, инструменты, память, итерации, рефлексия, перебор вариантов. Это то же самое, что разница между калькулятором и человеком с карандашом — калькулятор быстрее в арифметике, но в задачах, требующих структуры, человек с хорошим методом побеждает.

### 2. Фреймворк — это экзоскелет для модели
- **Память** компенсирует маленькое контекстное окно
- **Инструменты** компенсируют слабые знания (поиск вместо запоминания)
- **Планирование** компенсирует слабый planning в маленьких моделях
- **Итерации** компенсируют неточность (10 попыток вместо 1)
- **Рефлексия** компенсирует невозможность самокритики
- **Декомпозиция** компенсирует сложность одной задачи

### 3. Старое железо — не отходы, а compute
Каждый выброшенный ноут — это CPU + RAM + диск + сеть, которые могли бы работать. Если 10 старых ноутов объединить в mesh, получается кластер, способный запускать несколько инференсов параллельно или шарить память для агента. **Цена = электричество, не аренда GPU.**

### 4. Автономность — главная фича, а не чат
O.S.A. — не чат-бот. Это **always-on агент**, который сам ставит себе задачи, планирует их, выполняет в фоне, не требуя пользователя в реальном времени. Человек приходит, ставит задачу, уходит — агент работает.

## Что такое «большие задачи» для O.S.A.

Не «универсальный ИИ», не замена GPT-4. Конкретный класс задач, которые маленькая модель в одиночку не решает, но решает с фреймворком:

- **Автоматизация рутины**: парсинг сайтов, обработка папок с файлами, мониторинг источников, конвертация форматов
- **Исследования и синтез**: найти 10 источников, прочитать, написать отчёт с цитатами
- **Кодинг**: написать скрипт по описанию, найти баг в существующем коде, рефакторинг
- **Анализ данных**: загрузить CSV, посчитать, сделать вывод, нарисовать график
- **Оркестрация длинных процессов**: «каждый день в 9:00 проверяй X и пиши мне в телеграм»
- **Knowledge work**: написать документ по черновику, составить резюме из кучи писем

Эти задачи — не тест на эрудицию (тут большая модель всегда выиграет). Это задачи, где **структура важнее знаний**. Тут фреймворк рулит.

## Три слоя (от простого к сложному)

### Слой 1. **OSA Runtime** (MVP, делаем сейчас)
Агент-процесс, который работает always-on на одной машине. Планировщик, память, инструменты, итерации, рефлексия. Прячется в свой sandbox, не трогает пользовательские файлы.

**Цель слоя**: доказать формулу «маленькая модель + scaffolding = большие задачи». Сделать 3–5 эталонных задач, которые агент решает лучше, чем та же модель без фреймворка.

**Стек**: Python 3.11+, SQLite, FastAPI (опционально), LLM-абстракция (Minimax сейчас, локальная 1B потом).

### Слой 2. **OSA Bare-Metal** (позже)
Агент умеет ставиться как единственная программа на пустое устройство. Минимальный Linux без пользовательских файлов. Устройство = терминал агента.

**Цель слоя**: устройство целиком становится ресурсом агента. Это и есть начало «дешёвого compute».

**Стек**: кастомный Linux-образ (buildroot / Yocto), свой init, A/B-партиции для OTA.

### Слой 3. **OSA Mesh** (ещё позже)
Несколько устройств соединены проводом (Ethernet). Агент автоматически обнаруживает соседей, распределяет задачи, шарит память и inference. Нода умерла → задачи мигрируют на соседнюю.

**Цель слоя**: распределённый мозг из старого железа. Куча списанных ноутов + десктопов + Raspberry Pi = один мощный агент.

**Стек**: mDNS/Avahi для discovery, gRPC для IPC, своё хранилище (или IPFS-lite), планировщик задач с учётом ресурсов нод.

## Принципы

1. **Scaffolding важнее модели.** Лучше плохая модель с хорошим фреймворком, чем хорошая модель с плохим.
2. **Прозрачность работы.** Агент логирует каждый шаг. «Завис», «не знаю», «не хватает ресурса» — допустимые ответы. Молчаливый fail — нет.
3. **Локальность по умолчанию.** Данные не уходят в облако без явной причины. Minimax API на старте — временная мера.
4. **Graceful degradation.** Сеть упала → работаем на одной ноде. API недоступен → переключаемся на локальную модель. Память кончилась → честно говорим.
5. **Измеримость.** Любая гипотеза проверяется цифрами. «Работает» не катит — нужно «решает задачу X за Y секунд с точностью Z».
6. **Никакого vendor lock-in.** Свой код, MIT-лицензия, заменяемые компоненты.

## Чего НЕ будет (границы MVP слоя 1)

- ❌ UI в браузере. CLI + локальный дашборд.
- ❌ Мультиагент (несколько ролей). Один агент, но с богатым инструментарием.
- ❌ Bare-metal install. Это слой 2.
- ❌ Mesh. Это слой 3.
- ❌ Облачная SaaS-версия. OSA — то, что ставится на твоё железо.
- ❌ LangChain / AutoGen / CrewAI как зависимости. Свой код.
- ❌ Гонка за фичами. Сначала фундамент, который не падает.

## Риски (честно)

- **Масштаб mesh-слоя**. Это годы для команды. Один разработчик с хобби-графиком — реально не потянет всё сразу. → Митигация: этапы, MVP каждые 2–4 недели, отсечение лишнего.
- **Своя 1B-модель пока не готова**. Зависимость от Minimax. Квоты, цена, изменения API. → Митигация: абстракция `LLMProvider`, fallback на локальный stub.
- **«Агент сам ставит себе задачи»**. Это риск runaway: агент уходит в бесконечный цикл и жрёт ресурсы. → Митигация: rate-limits, watchdogs, обязательный лимит итераций на задачу.
- **Время — конечный ресурс**. Обучение LLM закончится, свободное время исчезнет. → Митигация: каждый этап должен заканчиваться **работающим артефактом**, а не «почти готово».
- **Маленькая модель + сложный scaffolding = долгие ответы**. Цикл «подумал → попробовал → упал → попробовал ещё» может занимать минуты. → Митигация: чёткие timeouts, прогресс-бары, кеширование.
